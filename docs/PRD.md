# PRD：MMEETT Fate 重构

## 产品目标

将当前 MMEETT Fate 原型重构为一个连贯的网页产品。用户能够按自身意图进入，理解哪种推演方式适合自己的问题，完成一段聚焦的交互，并通过清晰结构、来源引用和克制设计建立对结果的信任。

## 目标用户

- 对中国命理、卜筮、塔罗、择时、关系和人格探索感兴趣的用户。
- 希望快速查看每日提示、收藏工具或重复使用推演流程的回访用户。
- 负责维护本项目的设计师和开发者，他们需要在修改 UI 前看清产品和技术全貌。

## 问题说明

当前原型覆盖了大量功能，但优先级不清晰。工具、内容系统、游戏，以及现代心理与关系模块同时呈现，让用户先感受到“很多”，却难以先理解“是什么”。重构需要把现有功能清单转化为分阶段、可理解的产品体验。

## 本阶段范围

- 围绕用户的问题与意图重新定义主要信息架构。
- 第一阶段首页结构以 `docs/homepage-function-map.md` 为准：今日命理场、意图推荐区、回访与每日使用、结果可信度展示、更多探索和页脚。
- 将现有较成熟的模块保留为可复用产品能力。
- 重构首页和关键流程，建立清晰的视觉层级、响应式行为和有意义的交互状态。
- 通过古籍、图解和可解释的结果结构，呈现内容可信度。
- 保持 Vite 本地原型稳定运行。
- 通过 CCPM 的 PRD、Epic 和后续任务文件跟踪工作。

## 暂不包含

- 未经明确授权的自动生产部署或公开发布。
- 宣称当前演示算法已达到生产级专业命理能力。
- 支付、真实会员体系或完整后端实现，除非另行确定范围。
- 将 `dist/` 作为源代码手工修改。
- 在第一阶段重构全部 28 个工具。

## 主要用户路径

### 路径 1：首次访问

验收标准：

- 用户在“今日命理场”内理解 MMEETT Fate 是什么、今天的状态是什么、下一步可以问什么。
- 用户可以按五类问题入口选择路径：看自己、看关系、问当下、查日子或学知识。
- 第一屏不依赖密集的工具名称列表来完成表达。

### 路径 2：选择推演路径

验收标准：

- “意图推荐区”根据当前问题推荐 1 个主工具和 2 个备选工具。
- 在展示表单前，先让用户知道需要提供哪些信息。
- 工具结果将结构化依据与解读内容分开呈现。

### 路径 3：每日轻量使用

验收标准：

- 用户可以在“回访与每日使用”中快速继续上次推演、打开每日一卦或生成今日分享卡片。
- 需要按天固定的结果，在同一天内保持一致。
- 分享/保存操作必须真实反映当前实现状态。

### 路径 4：学习与验证

验收标准：

- “结果可信度展示”必须包含推演依据、古籍出处、知识图解和术语解释四层。
- 术语在当前上下文中得到解释，不要求用户另开一段完整阅读流程。
- 内容层不能压过当前主要操作。

## 功能需求

- 首页意图入口系统，具体结构见 `docs/homepage-function-map.md`。
- 核心工具卡片与引导式路由。
- 重新设计选定 A 级工具的展示方式。
- 内容可信度层：古籍、藏经阁和知识图解。
- 本地持久化的主题、语言和收藏。
- 清晰的会员/登录边界。
- 足够支持未来 Agent 接手的文档和管理文件。

## 非功能需求

- 支持桌面端和移动端响应式布局。
- 文本不得与其他内容重叠，也不得溢出控件。
- 视觉设计应通过构图、动效和状态表达产品，而不是依赖大段解释文字。
- 动效必须服务于状态变化、用户反馈或产品情绪。
- 引入明显动效时，应支持减少动态效果的系统偏好。
- 交接前必须通过本地标准检查命令。

## 成功标准

- 新维护者可以在 20 分钟内通过仓库文档理解范围、入口、风险和后续步骤。
- `npm run check` 可在本地通过。
- 第一阶段重构完成桌面端和移动端真实页面验收。
- 第一阶段首页主要用户入口不超过 5-7 个。
- 范围外模块明确停放在路线图中，不做半成品式重构。

## 约束与假设

- 当前源代码是前端原型。
- 当前工作目录中没有后端源代码。
- 现有数据和算法可以用于 UI 原型，但在用于生产级声明前必须经过验证。
- 用户希望根据功能重新构造网页，而不是原样保留当前布局。
- 发布需要用户明确确认。

## 当前阶段验收标准

- 长期项目管理基线已建立。
- 功能图已建立。
- CCPM PRD 和 Epic 已建立。
- 质量检查命令已存在且可运行。
- 已知风险已记录。
