# PRD：fate-rebuild

## 概要

将功能庞杂的 MMEETT Fate 复刻原型，重构为可以分阶段实施和长期维护的网页产品。首要目标是把现有功能清单转化为清晰的信息架构和重构路径。用户应当按照自己想了解的问题进入，完成一段聚焦的交互，并看到有依据支持的结果。

当前首页方向已由用户确认，并记录在 `docs/homepage-function-map.md`。后续首页设计和实现以该文件为准。

## 问题说明

当前项目已经包含大量页面、工具、游戏、内容系统和支撑功能。问题不在于功能不够，而在于优先级和产品框架不清晰。长期重构需要稳定的单一事实来源、分阶段范围，以及更小的第一阶段交付单元。

## 用户故事

### 首次访问者

作为首次访问者，我希望在第一屏内理解 MMEETT Fate 能做什么，以便决定是否继续。

验收标准：

- 第一屏作为“今日命理场”，传达品牌定位、今日状态、五类问题入口和每日轻量入口。
- 用户无需阅读全部工具名称，就能选择看自己、看关系、问当下、查日子或学知识。
- 页面不会把全部 28 个工具作为用户的第一个选择。

### 回访用户

作为回访用户，我希望快速打开熟悉的工具或每日提示，避免重复查找。

验收标准：

- 收藏功能保持可用。
- 回访与每日使用区提供继续上次推演、每日一卦和今日分享卡片。
- 从首页进入核心工具最多需要两次操作。

### 带着具体问题的用户

作为带着问题来的用户，我希望产品引导我找到合适的方法，让结果显得有结构，而不是随机给出。

验收标准：

- 界面区分看自己、看关系、问当下、查日子和学知识等路径。
- 意图推荐区为当前问题推荐 1 个主工具和 2 个备选工具，并在开始前说明需要提供的信息。
- 结果页将结构化依据与解读内容分开呈现。

### 维护者

作为维护者，我希望项目状态、路线图、架构和质量命令都有文档记录，以便后续任务无需重新调查基础信息。

验收标准：

- `PROJECT_STATE.md`、`docs/ROADMAP.md`、`docs/ARCHITECTURE.md`、`docs/QUALITY.md` 和 CCPM 文件均已存在。
- 标准质量检查命令已有记录。
- 已知风险和发布门槛已有记录。

## 功能需求

- 创建并维护长期项目基线文件。
- 将当前功能图保留为源功能清单。
- 围绕用户意图定义第一版重构信息架构。
- 维护 `docs/homepage-function-map.md` 作为首页设计和实现准则。
- 确定适合分阶段重构的 A 级核心工具。
- B 级工具保持停放或框架状态，直到明确决定提升优先级。
- 保持本地 Vite 开发流程可用。
- 发布和公开上线必须经过用户明确授权。

## 非功能需求

- 重构结果必须支持响应式，并经过视觉验证。
- UI 文字必须在桌面端和移动端容器内正确显示。
- 动效必须服务于产品状态和用户反馈。
- 代码库必须明确区分源代码与生成产物。
- 本地检查统一通过一个标准命令运行。

## 成功标准

- 新 Agent 可以依靠仓库文档接手项目。
- UI 重构开始前，第一阶段范围已经明确。
- 首页核心信息架构收敛为意图路径和少量主要操作。
- 扩展前至少重构并完成视觉验证一条核心工具流程。
- 未经当前任务明确授权，不进行部署或公开发布。

## 约束与假设

- 当前源代码仅包含前端。
- 除非另行验证，当前算法和解读均视为演示数据。
- 当前工作目录中没有后端登录/会员基础设施。
- 用户希望依据功能重新构造网页。
- 在任何公开发布前，当前项目可能继续在本地演进。

## 暂不包含

- 在第一阶段完整实现全部 28 个工具。
- 后端会员、支付或用户档案系统。
- 公开部署。
- 离线单文件打包。
- 宣称具有专业预测准确性。

## 依赖

- `docs/fate-function-map.md` 中现有的功能源图。
- Vite/React 工具链。
- 用户确认第一阶段范围和设计方向。
- 未来可选的登录与会员后端。
